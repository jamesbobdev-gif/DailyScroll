# Daily Scroll on Android as a sideloaded APK

This is the "works today" route for phones: build an APK on this PC, copy it to an Android phone, and point it at the Daily Scroll service running on the same Wi-Fi. No store account, no review, no hosting. Everything the Windows app does on the phone side is here, with the limits listed at the end.

## What was set up on this PC

The Android toolchain lives outside the repo so nothing is committed by accident:

| Piece | Where | Notes |
| --- | --- | --- |
| JDK 17 (Temurin) | `C:\Android\jdk17` | unzipped, no installer |
| Android SDK | `C:\Android\sdk` | command-line tools, platform-tools, platforms 36 and 37.0, build-tools 36.0.0 and 37.0.0, NDK 27.1, CMake 3.22 |
| Native project | `android/` in the repo | generated by `npx expo prebuild`; it is git-ignored and can be regenerated at any time |

Repo changes that make the build work:

- `app.json`: app icon, adaptive icon and splash from `assets/`, `versionCode`, and the `expo-build-properties` plugin with `usesCleartextTraffic: true`. Without that last setting a release APK refuses to talk to the service over plain `http://` and shows "The service is unavailable" forever.
- `assets/`: generated placeholder icon and splash (dark green with a "DS" timer mark). Replace them with real artwork whenever you like; keep the file names.
- `.gitignore`: `android/` and `ios/` are ignored because Expo regenerates them.
- `package.json`: `npm run android` now runs `expo run:android` (Expo changed this during prebuild).

## Build the APK

From the repository root:

```bash
npm ci
npx expo prebuild --platform android --clean --no-install
```

Then build (PowerShell or Git Bash):

```bash
cd android && JAVA_HOME='C:\Android\jdk17' ./gradlew.bat assembleRelease
```

The APK lands at `android/app/build/outputs/apk/release/app-release.apk`. The first build downloads Gradle and dependencies and takes a while; later builds are a few minutes.

`android/local.properties` must contain `sdk.dir=C:/Android/sdk` (forward slashes; backslashes are treated as escape characters and break the path). Prebuild with `--clean` deletes the folder, so recreate that file if Gradle complains it cannot find the SDK.

The release APK is signed with the project's debug keystore. That is fine for installing on your own phones. If you ever publish, create a real keystore and set it in `android/app/build.gradle`, and keep the keystore out of Git.

## Install it on a phone

1. Copy `app-release.apk` to the phone (USB, Google Drive, email to yourself, or `adb install`).
2. Open the file on the phone. Android asks to allow installs from that source the first time; accept.
3. Start the service on this PC from the repo root: `npm run service` (testing mode, no time limit) or `npm run service:limited` (real one-hour allowance).
4. In the app's first screen, type the PC's Wi-Fi address with the port, for example `http://10.220.156.222:8787`, and tap Connect. Find the current address with `ipconfig` under the Wi-Fi adapter; it changes when you move networks. The address is remembered, and the small "Change service" link at the bottom of the picker switches it later.

Both devices must be on the same Wi-Fi. Windows Firewall already allows Node.js inbound on this PC. Some guest, campus or office networks block phone-to-laptop traffic; if Connect fails on one of those, use the phone's hotspot and join the PC to it instead.

To put a fixed address into the build so the setup screen never shows, set `EXPO_PUBLIC_SERVICE_URL=http://ADDRESS:8787` in the environment before running prebuild and Gradle. Leave it unset for a build you want to repoint later.

## Reaching the service away from home

The app is only a front end. Everything it shows comes from the Node service, so the phone must be able to reach a running copy of it. Three ways, from quickest to proper:

1. **Same Wi-Fi** (above): type the PC's address. Works at home, nowhere else.
2. **Public tunnel from this PC**: `cloudflared` is installed for the current user. With the service running, open a second terminal and run the command below. It prints an `https://something.trycloudflare.com` address; type that into the app and the phone can connect over mobile data from anywhere, as long as this PC stays on and the tunnel stays open. The address changes every time the tunnel restarts, and anyone who guesses it can reach the service, so treat it as a demo link, not a deployment.

   ```bash
   npm run tunnel
   ```

   That runs `cloudflared tunnel --url http://localhost:8787`. If the command is not found, open a new terminal first; winget added `cloudflared` to the PATH after installation.

3. **Hosted service** (the real fix): deploy with the repo's `Dockerfile` to a small host (Fly.io, Render, Railway or a VPS), with HTTPS, a persistent volume for `data/`, and `PUBLIC_ORIGIN`, `COOKIE_SECURE=1`, `TOKEN_ENCRYPTION_KEY` set. Then rebuild the APK with `EXPO_PUBLIC_SERVICE_URL` pointing at it so the address screen never appears. Creating the hosting account is the one step that has to be done by the account owner. Step-by-step instructions for Fly.io are in [HOSTING.md](HOSTING.md).

## What works and what does not

Works on the phone side of the code: the picker, the timer, pause and resume, All apps and Android Back returning to the picker, tabs per platform, rooms and saved posts through the service page, and the one-hour allowance when the service runs in limited mode.

Known limits that are not fixed by the APK:

- Google sign-in inside the YouTube view is blocked by Google in embedded browsers. Other platforms may push you to their own apps or refuse login. Signed-out browsing works; signed-in feeds are not guaranteed.
- The service only runs while this PC is on and on the same network. Away from home the app shows "Could not reach the service".
- The APK was verified on the Android 16 emulator on this PC (Pixel 7 profile): connect to the service, picker, YouTube Home and Shorts, Instagram, Pause, Android Back and All apps returning to the picker. It has not yet been run on a physical phone. The first real-phone test should cover: connect over Wi-Fi, each platform loading, video playback with sound, pause, background and return, Back, and running the hour down in limited mode.

## Emulator on this PC

A Pixel 7 virtual device named `dailyscroll` on Android 16 exists for testing without a phone. Start it, then install the APK and point the app at `http://10.0.2.2:8787`, which is the emulator's alias for this PC:

```bash
C:/Android/sdk/emulator/emulator.exe -avd dailyscroll -no-snapshot -no-audio -gpu swiftshader_indirect
```

```bash
C:/Android/sdk/platform-tools/adb.exe install -r android/app/build/outputs/apk/release/app-release.apk
```

Video renders as a black frame under the software GPU in the emulator; that is an emulator limit, not an app bug.
